# Agent Note: GC discovery 选择 GFXHUB 3.0 / 3.0.3，覆盖最早的 fault IRQ 写入

Status: implemented

## Problem

Linux v6.12 的 `gmc_v11_0_set_gfxhub_funcs` 只为 GC 11.0.3 选择 `gfxhub_v3_0_3`，GC 11.0.2 使用 `gfxhub_v3_0`。项目却始终 include `gc_11_0_3_gmc.h`；不仅 level 7 的页表、cache、TLB flush 会写错，level 6 的 `gmc11_set_vm_fault_interrupts` 已先写错 context control。固件与 PM 准备不能修正这些寄存器。

GFXHUB 在 level 7 已启用，GFX ring 却到 level 8 才分配；清理依赖 `fGfx` 会使 level 7-only、启用后 SDMA 失败及 level 8 GFX 分配失败的路径漏关 hub。

## Decision

- `gmc11_init` 在分配显存或访问寄存器前检查实际 discovery 的 GC present、segment 0 数量和版本，只接受本次确知的 11.0.2 / 11.0.3；失败复用原 `GMCResult` / `failed: GMC` 路径，并记录 present、segment 数和完整版本。不以 PCI ID、revision 或营销名称选择，也不把未知 GC 默认成 Navi32。合法 segment 0 基址为 0 时仍接受。
- GFXHUB 的生产入口统一命名为 `gfxhub11_*`，内部必须在成功的 `gmc11_init` 后使用。寄存器按 GC 选择完整的两套 offset，而不是统一减一个常数：例如 context control 为 `0x1688 / 0x1698`，页表基址为 `0x16f3 / 0x1703`，L2 control 为 `0x15bc / 0x15c0`。两个布局的本次寄存器全部属于 discovery segment 0；实际使用的 119 个 field shift/mask 和 context / engine strides 已逐项与固定官方头核对一致，继续共享算法。
- 新 `gc_11_0_0_gmc.h` 由仓库 `tools/gen_regs.py` 从固定 Linux v6.12 的 offset / mask / default 原文提取现有 GMC 同组寄存器及 CP_DEBUG，再保留寄存器、BASE_IDX、三个 cache default 和所需 CP_DEBUG bit，统一加 `GFXHUB30_` 前缀，避免与原 11.0.3 宏冲突。原 11.0.3 头文件及既有 cache default 行为保持不变，不顺手修订上游其他差异。
- 选择贯穿 GART 初始化、早期 IRQ、fault status 的两次读取与清除、disable、页表设置、CPU flush，以及 GFX / SDMA / Bringup 的 ring 内 flush register helper。不存在旧 `gfxhub303_*` 兼容别名。
- `gfxhub_v3_0_set_fault_enable_default` 的 CP_DEBUG `CPG_UTCL1_ERROR_HALT_DISABLE` bit15 用读改写置位，保留其余位；11.0.3 不访问它。11.0.2 同时保留 Linux 的语义：value 为 false 时置 crash bits，true 时不擅自清除原 crash bits。11.0.3 延续项目原来的 crash bit 行为。
- Bringup 的 fini / suspend 使用已有 `gfxhub_enabled` / `mmhub_enabled` 标志，初始化拒绝后不因分配了空 GMC 对象就访问未初始化的 hub。GFXHUB 清理与 `fGfx` 解耦；`gfxSuspend` 仅在 GFX ring 存在时执行 ring 操作，`stopAndFree` 保留原 `fAmdgpuExact` 策略。`gfxhub11_gart_disable(d, g)` 完成 MMIO 后清除 `g->gfxhub_enabled`，重复清理不再访问已关闭的 hub。不在所有内部 helper 重复检查 discovery，也不引入 ops 框架、新开关或未来版本兼容层。
- MMHUB 仍是既有实现；这里没有能证明本机 MMHUB IP 版本与全部显示寄存器布局的 discovery 证据，不根据卡名顺带重构。

### Testing

`tests/sim_gfxhub11.inc` 由现有 `sim_navi32` 包含并无条件运行，不需要固件文件。它调用生产 C 和原有 `rdna3_dev_set_discovery`，独立数值 fixture 分别运行 GC 11.0.2 / 11.0.3、合法零基址 / 非零基址、一个 / 三个 segment：

- level 6 顺序的全部 16 个 IRQ context，保留其他位；level 7 真实 `gfx11_gfxhub_enable` 的完整 MMIO 写地址集合、页表地址、全部 VMID、cache、invalidation ranges、fault defaults 和 CPU ACK / timeout。
- 11.0.2 的旧 11.0.3 context / PT / L2 地址哨兵不被写入，segment 1 不被误用；CP_DEBUG bit15 的读改写，以及 11.0.3 不触碰 CP_DEBUG 的回归。
- fault status 的第一次 stale 读取、第二次真实读取、decode / clear；PT setup、flush registers、真实 GFX / SDMA emitter 的 packet 地址与字段、disable 的两版 MMIO 结果、`gfxhub_enabled` 从 1 清零和 FB offset。
- 缺失、缺 segment、未知 major / minor / revision 在 `gmc11_init` 拒绝，零 MMIO、零显存写入、零分配。仅缺失 GC 的一轮预期 `rdna3_dev_set_discovery` 返回 `RDNA3_ENODEV`，其余轮仍要求 `RDNA3_OK`，之后照常验证 GMC 拒绝且无副作用。内部 helper 不接受未初始化对象，测试不制造此类无效调用。

`tests/test_gfxhub_lifecycle.py` 完整提取生产 `gfxSuspend`，并提取 `stopAndFree` 实际的 hub guard / call，编入轻量 C++ harness 执行状态断言。覆盖无 `fGfx` 但 hub 已启用、hub 关闭、缺 device / GMC、正常 async / legacy ring、未 ready 的 KIQ、部分 GFX 初始化及重复清理；同时保留非 exact stop 不关闭 hub 的策略。harness 使用生产类型与函数声明，disable stub 的清零契约由上述真实 C 测试交叉约束，不把源码匹配当运行证据。

根 `Makefile` 为 simulator 显式加入新 `.inc` prerequisite，并在共享 `COMMON_H` 加入两份 GMC 生成头，覆盖所有实际编译 GMC 的 host 目标；`PY_TESTS` 纳入生命周期 harness。`kext/Makefile` 现有 `HDRS` 已收集 `../hw/gen/*.h` 并供全部对象依赖，不需要改动。

针对性执行入口是 `make t.sim_navi32 t.test_gfxhub_lifecycle`；完整 `make test` 的 ASan/UBSan 和 macOS 15 native 编译由根代理汇合后执行 GitHub CI。本次 Windows 环境未发现 clang / clang++ / gcc / cc / make；Python 语法与生产源码提取离线检查通过，但直接运行生命周期测试在启动 clang++ 时以 `FileNotFoundError: [WinError 2]` 失败，尚未执行 C++ 状态断言。未运行 C 测试或 native 编译，不能将新增断言写成已通过；独立源头数值核对、`git diff --check` 与 Note 门禁不替代这些检查。

## Alternatives considered

- **只改 level 7 的 enable 或把所有寄存器统一减 `0x10`**：diff 最小，但遗漏更早的 IRQ、fault decode 和 ring 内 flush，且 L2 一组只差 `0x4`、部分 aperture offset 完全相同，必然误写。
- **从 PCI 7480 或 RX 7600 XT 名称选择布局**：绑定层容易取得，却不能证明真实 GC IP，且会把相同硬件布局与产品名称耦合，故沿用 discovery。
- **复制两份完整 GMC 算法或引入可扩展 ops / 映射对象**：能隔离全部版本，但本次只涉及两组寄存器和一个确证的 CP_DEBUG 差异；验证相同字段后共享算法更小，未知版本由输入边界明确拒绝。
- **在每个 helper 检查 GC 或让未知版本回退 Navi32**：前者重复内部不变量，后者掩盖缺失真实输入。采用初始化边界与既有生命周期标志，拒绝后不执行清理 MMIO。
- **继续用 `fGfx` 是否分配代表 GFXHUB 是否启用**：可省去状态参数，但 level 7 已启用 hub，无法覆盖部分初始化；以已有 `gfxhub_enabled` 为准，并让真实 disable 对称清零，不新增生命周期包装层。

## Consequences

新增跟踪的 Linux `gfxhub_v3_0.c` 独立列入 `GFXHUB 3.0` 状态组，不沿用旧 Navi32 的 level 6/7 实卡通过记录；新组硬件通过数必须保持 0。仅有实际源函数名注释的项目按既有规则计作已移植，不为改善百分比补写未经逐函数核验的标签。

收益是修正一个真实可达的 Navi33 图形内存控制器适配缺口，同时保留 11.0.3 的已有效路径。代价是维护两套寄存器来源；以后新增 GC 版本必须重新核对 offset、field、stride 和上游专用步骤，不能只扩展版本白名单。
