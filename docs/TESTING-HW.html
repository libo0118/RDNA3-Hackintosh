Hardware test: step-by-step ladder

The step-by-step ladder for a hackintosh with an RX 7800 XT: the boot-args of each step, what to check, how to report, and the bare-metal run with the installer. For the owner and anyone testing on the real card.

  5. Bare metal with the installer (no VM harness)

A single procedure for a hackintosh with an RX 7800 XT. Do you have Linux and this card as the only one? The same ladder runs in a virtual machine, automated: TESTING-VM. Each step adds one thing, and after each one you collect a report with a single script. If a step hangs the system or turns off the screen, go back to the previous one and send the report from it together with a description of the symptom. Module details are in STAGE1–STAGE7.

Before the first step

  1. A way back. In OpenCore keep a second entry or a second copy of the EFI in which the RDNA3 kexts are disabled. The boot-arg -rdna3off also disables everything. Check once that you can edit boot-args in the picker (space, then the entry with boot-args, or Cmd+V for verbose mode).

  2. Remote access. System Settings → General → Sharing → Remote Login (SSH). When the screen goes dark, you collect the report over SSH from another computer.

  3. BIOS. CSM disabled, Above 4G Decoding enabled. With Resizable BAR on, set Booter → Quirks → ResizeAppleGpuBars = 10 (1 GiB) or 8 (256 MiB) in OpenCore, or turn Resizable BAR off: macOS takes no BAR above 1 GiB, a 16 GiB BAR0 leaves the kext with no VRAM aperture (DRIVER-PLAN N62, docs/INSTALL-OPENCORE.html section 5).

  4. Build and install. On the Mac, in the repository directory:

    make kext && make -C userspace && make tools
make -C accel && make -C fb          # accelerator and framebuffer (from step 9)
sudo package/install.sh --fw /path/to/linux-firmware/amdgpu

    Firmware is not in the repository (docs/FIRMWARE.html). The installer rebuilds the Auxiliary Kernel Collection; a restart is required.

    Through OpenCore instead (recommended): kernelmanagerd may refuse ad-hoc signed kexts in the Auxiliary KC ("invalid codeful kernel extension", seen in the VM). Then let OpenCore inject them:

    sudo diskutil mount disk0s1                   # your EFI partition (diskutil list)
sudo package/oc_install.sh --efi /Volumes/EFI --fw /path/to/linux-firmware/amdgpu
sudo package/oc_install.sh --efi /Volumes/EFI --step 2     # boot-args of a step
sudo package/oc_install.sh --efi /Volumes/EFI --off        # everything off again (-rdna3off)
sudo package/oc_install.sh --efi /Volumes/EFI --remove     # our kexts, entries and boot-args out of OpenCore

    It copies the kexts to EFI/OC/Kexts, adds them to Kernel/Add, puts the firmware in /Library/Application Support/RDNA3/firmware, and sets the step's boot-args in config.plist (yours other than rdna3* stay; a backup config.plist.rdna3-<date> is written first). With this route skip step 5 below: --step N does it.

  5. Set boot-args once per step, for example:

    sudo nvram boot-args="-v keepsyms=1 rdna3lvl=2"

    Keep your existing boot-args and append the ones from the table.

  6. Report after each step (after the restart, from a normal terminal or SSH):

    tools/macos/collect.sh step3

    The script changes nothing. It creates ~/rdna3-report-step3-<date>.tar.gz with logs, IORegistry, boot-args and a panic report, if any.

Sleep: from level 4 on, without rdna3resume=1, the kext keeps macOS from idle sleep (RDNA3,IdleSleepBlocked = 1): without the resume the firmware and the GOP's picture are gone after a sleep. Do not put the machine to sleep by hand during such tests; rdna3sleep=1 lifts the block. rdna3resume=1 (step sleep, big4) is the suspend and resume: the clients' VRAM saved to system memory and the IPs suspended (amdgpu_device_suspend) before the sleep, the GPU posted and brought up again on the wake, the VRAM and the display state restored; the machine then idles to sleep like with any other GPU (see docs/DRIVER-PLAN.md, D4, for what is still missing).

Sensors: once the SMU is up (level 6 and higher) RDNA3Accel publishes PerformanceStatistics every 2 s, with the keys AMD's macOS drivers use (Temperature(C), Junction Temperature(C), Fan Speed(RPM), Core Clock(MHz), Memory Clock(MHz), Total Power(W), Device Utilization %). Check with ioreg -rc RDNA3Accel -d1 | grep -A9 PerformanceStatistics; the values must change under load and the temperature must look plausible (30-90).

Rule: do not move on until a step gives the expected values. When a result differs from the table, send the report. That is exactly the information that cannot be obtained in the simulator.

When something goes wrong

Symptom What to do
hang at boot on step N restart with the boot-args of step N−1 (OpenCore picker) and a report from that boot; describe at which point of the verbose log it stopped
kernel panic after the restart collect.sh attaches the two latest panic reports by itself
no login window or desktop (WindowServer never reaches the GPU) do not stop the VM: the boot watchdog in the report daemon takes its evidence (sample, logs) about 4-5 min after the start and once more a minute later; rdna3vm then stops the VM by itself and the card comes back to Linux (about 6 min in all). Stop it by hand only if nothing happened after 10 min
black screen, system alive SSH, tools/macos/collect.sh screen, then sudo nvram boot-args="..." without the last flag and sudo reboot
no RDNA3 entries at all in the log the kext did not load: 03-kexts.txt and kmutil showloaded; check that the installer rebuilt the collection and that SIP allows kexts from /Library/Extensions
RDNA3,PSPResult other than 0 firmware is missing from RDNA3Accel.kext/Contents/Resources or it is a different version than expected; send the report

What cannot be checked without the card

The simulator models the behaviour from the Linux code, but it does not know how the card will really behave. The first test will tell us above all:

  • whether PSP accepts our firmware loading order (step 4);
  • whether PMFW accepts the BoardTable from the VBIOS and the safe feature set (step 5);
  • whether resetting DMCUB under a live GOP image is safe (step 5b);
  • whether the GPU executes our SDMA and PM4 packets (steps 7 and 8);
  • how IOAcceleratorFamily2 fills IOAccelConfig before us (step 10).

Further modeset work (DML, pixel clock, DP training) starts after steps 2, 5b and 9, because it needs real DCN register values.

Bare metal with the installer (no VM harness)

For a hackintosh where the driver is installed with the .pkg (or the tarball's install.sh) instead of a build tree: INSTALL-OPENCORE covers the package, the OpenCore settings and the way back. Everything below runs from /Library/Application Support/RDNA3 (written $R here); nothing needs the repository or a Linux host.

  1. Way back first (INSTALL-OPENCORE §8): a USB copy of the EFI with RDNA3Accel.kext disabled and -rdna3off. SSH on (Remote Login), so a dark screen still gives a report.

  2. Install: the .pkg, then sudo "$R/oc_install.sh" --efi /Volumes/EFI (EFI mounted) for the OpenCore entry of the core kext. Check the security settings of INSTALL-OPENCORE §4 (csr-active-config, SecureBootModel, amfi=0x80). Restart, Allow in Privacy & Security if asked, restart again.

  3. Boot with the default profile: no rdna3 boot-args at all. Expected: the desktop on the RX 7800 XT at the GOP resolution, a second monitor as an extended display, ioreg -rc RDNA3Accel -d1 | grep -E 'Stage2|GFXResult|PMFeatures' shows the bring-up done.

  4. Report (after the desktop is up, from Terminal or SSH):

    sudo "/Library/Application Support/RDNA3/autoreport.sh" --standalone

    The same tests and report the VM runs after each boot (tools/vm/macos/autoreport.sh): scanout pictures, display sleep and wake, scaled mode switches, the DMA and GFX tests, Vulkan and Metal when installed, then collect.sh. It takes 3 to 8 minutes, a Terminal window shows the progress, and the files land in /Users/Shared/rdna3-reports/: rdna3-report-<label>-<date>.tar.gz, …-tests.txt, …-scanout*.ppm and the kernel's frame trace streamed through the whole run (…-trace-stream.bin, …-drmtrace-stream.bin, …-trace-sec.bin, each with a .size file; the archive holds copies as 36-stream-*.bin; the VM also sends WindowServer's plugin trace after each A/B phase as …-plugin-ab1-WindowServer-<pid>.trace and the like). Send all of them; they are what AFTER-TESTS expects from the VM.

    The rendering-artefact A/B (DRIVER-PLAN N50) is one command there too, in a Terminal on the Mac that has the card: sudo sh "/Library/Application Support/RDNA3/autoreport.sh" --standalone --ladder (about 29 minutes; --ladder-ws adds the two WindowServer rungs): Terminal and Chess open and close by themselves with one NVMTL_* switch per rung (right after the baseline attrring, DRIVER-PLAN N57: NVMTL_ATTR_RING_BIG_PAGE=0, RADV's GFX11 attribute ring without SPI_ATTRIBUTE_RING_SIZE.BIG_PAGE), it asks y / n / Enter for each rung's picture, and the report (41-ladder.txt, one triage row per rung, an automatic glyph verdict from each rung's hi-res look) says which switch made it right (AFTER-TESTS, "The whole ladder in one card run"). --ladder-glyphs (about 25 minutes) is the glyph hunt (managed uploads whole / in pages, the undeclared-write detector, the shared window surface, page-off, framebuffer fetch, ...).

    The app survey is the same machinery with the default driver: sudo sh "/Library/Application Support/RDNA3/autoreport.sh" --standalone --apps (VM: rdna3vm step apps, about 25 minutes). It opens Chess, Terminal, TextEdit, Calculator, Notes, Safari (a text / CSS page, a canvas animation, a WebGL cube; all made by the run, no network), Preview (a PDF and a JPEG), Maps, System Settings (three panes), App Store, Photos, Image Capture, QuickTime Player (a generated movie), Mission Control and Launchpad (Apps on macOS 26) one after another, takes a 320-wide and a hi-res look of both screens per app (…-scanoutapps-<app>[-<stage>]a|h-pipe<N>.ppm), says whether each ran, crashed or never opened, whether WindowServer survived, and quits it. Look at the pictures: the report says an app ran, not that it drew (AFTER-TESTS, "The app survey").

    Only the collection, without running any test: "$R/tools/macos/collect.sh" <label> (writes ~/rdna3-report-<label>-<date>.tar.gz).

    Black screens, windows that do not appear or flash, flicker? Instead of the report run the display bisect from a Terminal on the machine itself: sudo "/Library/Application Support/RDNA3/autoreport.sh" --standalone --bisect switches every new feature off and back on one at a time, 30 s each, while you look at the monitors (a notification, "step N" spoken, N beeps per step); press y (looks right), n (broken) or Enter (next) in the Terminal. --bisect-plugin does the Metal plugin's switches (WindowServer is restarted three times; log in again each time). --bisect-agdc is the kernel bisect over the switches that matter when WindowServer runs on the GPU (swap_mode, swap_gen, flipbuf_present, swap_stale, iop, a3, swap_latch, iop_flip; 13 combinations, not cumulative): use it on a machine booted with the agdc profile's boot-args, see TESTING-VM. The step list, the timetable and the reading of the result are in TESTING-VM; the same report files land in /Users/Shared/rdna3-reports/ (…-bisect.txt is new).

  5. A ladder step instead of the profile, when the default profile fails: sudo "$R/oc_install.sh" --efi /Volumes/EFI --step 2 (any step of the table above; --step default goes back to no rdna3 boot-args), restart, report as in 4. Walk up from the last step that worked.

  6. Roll back: --off (sets -rdna3off), the USB EFI, or from Recovery as INSTALL-OPENCORE §8 describes; sudo "$R/uninstall.sh" removes the install and, with the EFI mounted, its OpenCore part too (--keep-opencore skips that).

A dark screen with the system alive: SSH in, run step 4 there, then --off and restart.
