Instructions for a Linux computer in which the only graphics card is the RX 7800 XT (no iGPU and no second card). macOS runs in a QEMU virtual machine, and the card is passed through to it (passthrough). One script does everything: tools/vm/rdna3vm.

What it looks like in practice:

  1. You type rdna3vm step 2. The Linux desktop disappears, because Linux hands over the card.
  2. macOS appears on the monitor. It boots with our driver at the level for the given step.
  3. After about 2 minutes macOS collects a report by itself, sends it to Linux and shuts down. The Linux desktop comes back.
  4. The report is in ~/rdna3-vm/reports. You type the next step.

Time: one-time setup, about 1–1.5 hours (almost all of that time is the macOS installation). After that each step takes about 3 minutes.

During a step Linux has no display, and the keyboard and mouse belong to macOS. Every step logs you out of the Linux desktop: the desktop session holds the card, so the script stops the display manager to hand the card over and starts it again afterwards. You come back to the login screen; that is expected. Save your open work beforehand. You will not get stuck without a display, see Emergency exit: both Ctrl keys at once, then Esc 3×.

Step A. BIOS and Linux (once, 10 min)

Motherboard BIOS:

  • enabled: SVM (AMD) or VT-x (Intel);
  • enabled: IOMMU (AMD-Vi) or VT-d (Intel);
  • enabled: Above 4G Decoding;
  • disabled: CSM.

Resizable BAR can stay enabled.

Kernel parameter iommu=pt (on Intel also intel_iommu=on):

Distribution Command
Ubuntu / Debian / Mint in /etc/default/grub add the text iommu=pt to GRUB_CMDLINE_LINUX_DEFAULT, then sudo update-grub
Fedora sudo grubby --update-kernel=ALL --args="iommu=pt"
Arch (GRUB) like Ubuntu, then sudo grub-mkconfig -o /boot/grub/grub.cfg

Then restart the computer.

Packages:

Distribution Command
Ubuntu / Debian sudo apt install qemu-system-x86 qemu-utils python3 git dmg2img zstd psmisc
Fedora sudo dnf install qemu-kvm qemu-img python3 git dmg2img zstd psmisc
Arch sudo pacman -S qemu-full python git zstd psmisc; dmg2img is in the AUR

Finally, add yourself to the kvm group: sudo usermod -aG kvm $USER. Then log out and log back in.

Check:

git clone -b stage1-kext https://github.com/Voten641/RDNA3-Hackintosh ~/RDNA3-Hackintosh
~/RDNA3-Hackintosh/tools/vm/rdna3vm check

Every line should show OK. The script also shows what will go to the VM: the card (with its HDMI audio function) and the USB keyboard and mouse.

For convenience, set an alias. After that typing rdna3vm is enough:

echo "alias rdna3vm=~/RDNA3-Hackintosh/tools/vm/rdna3vm" >> ~/.bashrc && . ~/.bashrc

Step B. Downloading macOS (once, 10 min)

We use the existing OSX-KVM project:

git clone --depth 1 --recursive https://github.com/kholia/OSX-KVM.git ~/OSX-KVM
cd ~/OSX-KVM
./fetch-macOS-v2.py                      # choose Sequoia (macOS 15)
dmg2img -i BaseSystem.dmg BaseSystem.img

Step C. Driver package (once and after every new version)

  1. Open Forgejo → Actions (CI runs only there; GitHub just mirrors the code). Go to the latest green build run on the stage1-kext branch and download the RDNA3Accel-kext artifact (a .zip file). rdna3vm update does this for you (see "New driver version").
  2. Run:
rdna3vm prepare --osx-kvm ~/OSX-KVM --artifact ~/Downloads/RDNA3Accel-kext.zip

The script does, in order:

  • a copy of OpenCore with SIP disabled (required for an unsigned kext);
  • a package for macOS: kexts with firmware taken from /lib/firmware/amdgpu of your Linux;
  • a dump of the card's VBIOS;
  • reference data from amdgpu (reports/linux-reference), which we compare the results with.

It asks for the sudo password a few times.

Step D. Installing macOS in a window (once, ~1 h)

This step works without passing through the card: macOS opens in a normal window on the Linux desktop.

rdna3vm window

macOS runs at 1440x900 there (WINDOW_RESOLUTION in the config, or rdna3vm window --res 1280x800 for one run), not at the monitor's full size, and the picture is scaled to the window (QEMU's GTK zoom-to-fit): resize the window freely, the whole desktop stays visible. --no-zoom shows it 1:1. The steps with the card set the card's own mode back (OC_RESOLUTION).

  1. In the OpenCore menu choose macOS Base System.
  2. Disk Utility → choose QEMU HARDDISK (about 128 GB) → Erase: name macOS, format APFS. Close Disk Utility.
  3. Reinstall macOS Sequoia → choose the macOS disk. The installer restarts the VM several times by itself. If you see the OpenCore menu, choose the installer entry (macOS Installer), and at the end simply macOS.
  4. Create an account. You can skip Apple ID, location and other options.
  5. In macOS open Terminal (Cmd+Space, type "Terminal") and paste:
curl -s http://10.0.2.2:8000/setup.sh | sudo sh

This installs the driver and the automatic reports. When it finishes, shut down the VM with sudo shutdown -h now.

If macOS shows "System Extension Blocked": go to System Settings → Privacy & Security → Allow, restart and shut down the VM.

Step E. Tests on the card (about 3 min each)

Run the steps in order. Start the next one only when the previous one has come back with a report:

rdna3vm step 0

The desktop goes dark, OpenCore appears on the monitor, and then macOS with white text on a black background (verbose mode). About 2 minutes after the desktop appears, macOS shuts down by itself and the Linux desktop comes back. Then run the next steps:

Step hotplug is the one step that needs you at the screens: about two minutes after the desktop appears, the progress window and a notification say unplug and replug the second monitor now. You have two minutes from then: pull the second monitor's cable (the one the GOP did not light at boot), wait about 10 seconds, plug it back in. The report records what the driver saw (RDNA3,HPDState over time, the hotplug lines of the log) and takes a picture of both pipes afterwards. If you miss the window, the report says HOTPLUG: 0 HPD change(s); run the step again.

Display bisect (step bisect)

The screens have been wrong since about card run 58: black, windows that do not appear or only flash every few seconds, flicker. Since then several things were added; most have a switch that works while macOS runs. This step turns every one of them off, then on again one at a time (the oldest first, each one on top of the ones before it), and holds each state for 30 seconds while you look at both monitors. The report then says at which step the picture went wrong.

What you run:

rdna3vm update
rdna3vm step bisect

The VM boots as for any step. A few minutes after the desktop appears (the progress window says when) the 13 steps start; the whole run is 6.5 minutes and the report arrives a few minutes later. Nothing else runs in this step (no swap A/B, no Metal apps, no mode switches except the controls): the screens show the desktop and Activity Monitor (it redraws every few seconds, so a frozen picture shows). Only look at the monitors; do not touch the mouse or keyboard.

What you see and hear at every step: a macOS notification "step N of 12: ...", the voice saying "step N", and N short beeps (step 5: five beeps). If the virtual machine has no sound you still get the notification and the progress window; the timetable below tells you the step by the clock as well. Write down the numbers of the steps where a monitor goes black, a window does not appear or only flashes, or the picture flickers, and which monitor. The run also looks at the monitors itself (two pictures of every pipe per step) and sends what each step switched, so the report answers even without your notes.

Timetable (the time after the start; the progress window and the first notification say the clock time of the start). Each state is held for 30 s. "Off" is the value a switch has to restore the behaviour before it was added; the switches read back are in the report (39-bisect.txt).

Step Time What is switched Since
0 00:00 nothing: the defaults as the boot left them (the reference)
1 00:30 every new feature off: a3 0, flicker 0, swap_latch 0, swap_torn 0, swap_mode 0 (the flip), trace_scan 0, swap_stale 0 (closest to before the bug)
2 01:00 a3 1: applications' IOSurfaces live in the card's VRAM (A3) 2026-10-15
3 01:30 flicker 1: the flicker test hashes the swaps' pictures (reads the card's memory through the BAR) 2026-10-15d
4 02:00 swap_latch 1: a swap waits until its flip latched 2026-10-17
5 02:30 swap_torn 1: a second hash of every shown buffer 2026-10-17
6 03:00 swap_stale 1: the stale-back hold. This is the defaults again (the same switches as step 0; it only acts in mode 1/2) 2026-10-17c
7 03:30 control, off by default: swap_mode 1 (the back is copied into a scanout buffer instead of flipped to; the former default, it broke both monitors in the 2026-10-17d bisect) 2026-10-17b
8 04:00 control, off by default: trace_scan 1 (the trace samples the swap's other buffers) 2026-10-17b
9 04:30 control, off by default: swap_mode 1 with swap_landed 1 2026-10-17c
10 05:00 control, off by default: swap_mode 2 (every back copied) 2026-10-17b
11 05:30 control, off by default: a3ws 1 (WindowServer's own inputs in A3, the card run 58b flicker) 2026-10-15d
12 06:00 the defaults again (the end state; the switches are put back even if the run dies)

Steps 7 to 11 are controls: they show what the states that are off by default look like (swap mode 1 and 2, trace_scan, a3ws); a bad picture there is expected and does not count. Since card run 2026-10-17d the defaults are the flip (swap_mode 0) and trace_scan 0, i.e. the good state of that bisect, so step 0, step 6 and step 12 have the same switches (a different picture in them is reported as flaky). A step 1 that looks fine and a step 0 that does not means the cause is one of the switches above; the first of steps 2 to 6 that is bad again is the one that brings it back. If step 1 is bad too, none of these switches is the cause.

a3 and a3ws only reach surfaces created after the switch, so the run opens Activity Monitor again at steps 0, 1, 2, 11 and 12; every other switch acts at the next swap.

How to answer. By default the run is on a timer and records no answers (the triage uses its own looks: a lit pipe with almost no picture is black, a picture that stood still between two looks while it moved in other steps is frozen). To answer with the keyboard, start it by hand in a Terminal inside macOS instead:

rdna3vm args "rdna3bisect=3" --stay          # on the host: boots macOS, runs nothing
sudo sh "/Library/Application Support/RDNA3VM/autoreport.sh" --bisect    # in the macOS Terminal

Then press y (the picture looks right), n (broken) or Enter (next step) once a step is on; a key moves on to the next step after the run has taken its pictures (about 20 s into the step), no key = the 30 s timer. On bare metal (docs/TESTING-HW.html) the same with sudo sh "/Library/Application Support/RDNA3/autoreport.sh" --standalone --bisect.

The Metal plugin's own switches are the optional second run:

rdna3vm step bisect-plugin

Its steps: 0 the plugin as it is; 1 NVMTL_NO_SURFACE_SHARE=1, NVMTL_NO_SURFACE_PAGEOFF=1 and NVMTL_TRACE=0 in /Library/GPUBundles/rdna3mtl/rdna3mtl.conf and the %apps line out of the allow list (apps mode off); 2 the two NVMTL_NO_SURFACE_* lines out again (A3's plugin half, 2026-10-15); 3 apps mode back (2026-10-15); 4 the frame trace back (2026-10-17, the defaults again). The plugin reads its conf when a process loads it, so WindowServer is restarted at steps 1, 2 and 4: your session ends, the login window shows and you log in again (the run waits up to 5 minutes; if the guest logs in by itself nothing is needed). The risk is that of any WindowServer restart: the picture may stay black and the VM may panic (card run 50). The run uploads its table after every step, and the plugin's files are put back at the end and at the next boot should the run die. Run it last, and only when bisect points at nothing in the kernel.

This run is the default profile, where the AGDC is idle and WindowServer does no GPU work (it renders on the CPU). Its answer (swap mode 0 fine, mode 1 broken) therefore does not hold for the real desktop, which is the agdc profile: use bisect-agdc for that.

Not switchable at runtime (not tested by the steps above): the copy forward fixes of 2026-10-17 (rdna3accelcf=0 switches copy forward off for the whole boot), the visible-VRAM reserve (rdna3visreserve=<MiB>, 0 = none), output gamma on by default (rdna3gamma=0), the VRAM-lost CS refusal (rdna3vramlostcs=0), FreeSync (rdna3vrr=1, off by default), the VMID admission and every other change in the kext without a switch. Try those with rdna3vm args "<the boot-arg>" (no rdna3lvl in it: the default profile) and compare with step 0. Older than the bug and left alone: iop_async, crc_head and the plugin's NVMTL_NO_DIRTYONLY, NVMTL_NO_TEXBUF, NVMTL_SKIP_EMPTY, NVMTL_NO_BUFTEX_RECYCLE (all imported with the plugin on 2026-10-09; their defaults did not change).

The result: rdna3vm result prints the table (step, what changed, your answer, pipe 0 / 1 % not black, whether each picture moved between the step's two looks, the swap and stale-hold counter changes) and names the first step you marked n, the first whose looks went black or stood still, and where the run says the bug starts (BISECT: BREAKS AT step N). Anything missing (a look, the counters, a step that never ran) is a WARN.

Display bisect on the agdc profile (step bisect-agdc)

Card run 2026-10-17f (rdna3vm step play, swap mode 0): the desktop is broken again. The serial log says swap #83: head 1: the buffer it showed (phys ...) changed while on the panel ... rewritten in place and shown again and FRONT SURFACE sample: *** MOVED -- A LIVE WRITER IS PAINTING THE SCANNED-OUT SURFACE ***, and the second back buffer reads empty at every swap. The plain bisect could not have seen that: it boots the default profile, where the AGDC is idle and WindowServer renders on the CPU. bisect-agdc is the same 30-seconds-per-step bisect on the profile you really use.

rdna3vm update
rdna3vm step bisect-agdc

The boot-args are exactly those of step agdc (WindowServer on our Metal plugin: rdna3agdc=3 rdna3acceliop=1 rdna3accelfb=4 ...) plus rdna3bisect=4. (rdna3bisect=3 is "no tests this boot, start by hand", see above.) The run takes about 6.5 minutes of steps, the rest is the usual report (trace pump, plugin trace, collect.sh); the host stops the VM after about 23 minutes at the latest. Everything else is as in bisect: the notification "step N of 12: ...", the voice, N beeps, two pictures of each monitor per step (8 s and 20 s in) and the table in 39-bisect.txt / <report>-bisect.txt. Without keys the triage judges from the pictures (black, frozen). To answer with y / n / Enter, boot the agdc profile without tests and start the run in a macOS Terminal (the plain rdna3bisect=3 has no agdc profile, the AGDC would stay idle):

rdna3vm args "$(awk '$1 == "agdc" { $1 = ""; print }' tools/ladder-steps.txt) rdna3bisect=3" --stay
sudo sh "/Library/Application Support/RDNA3VM/autoreport.sh" --bisect-agdc    # in the macOS Terminal

All the switches can change at runtime (read from accel/rdna3-accel.cpp: swap_mode, swap_gen, swap_stale, trace_scan, swap_latch and iop_flip are read at every swap or import, flipbuf_present at every flip-buffer call, a3 at every IOSurface import, iop is a handler that publishes or removes IOAccelDisplayPipeCapabilities and makes the transaction hooks answer as the base class), so none was dropped. Three things the run cannot promise: a3 only reaches surfaces created after the switch (hence the reopened Activity Monitor); WindowServer may have read the pipe capabilities once at its start, so iop 0 may change only what the hooks answer; and after step 7 the later steps assume iop back at 1 really puts WindowServer back (step 12 has the same switches as step 0: a different picture there is reported as flaky or an order effect). iop is never written to the value it already has. The unswitched boot-args stay: rdna3gamma, rdna3accelcf and the rest are in the report's boot-args.

Evidence per step, on top of what bisect records: the swap counters at the step's start (the table subtracts them, so a delta is exactly one step), the trace position (trace_events_start / trace_events, stream_bytes_start / stream_bytes) so the decoder cuts the accelerator / DRM trace stream and the Metal plugin's trace per step (tools/rdna3_trace.py on the stream, events trace_events_start..trace_events), and one line trace: events W..W (asked by sysctl debug.rdna3accel_trace_dump) in the kernel log at each step's start (the serial log has no clock; the triage cuts the log by these lines). The trace pump runs for the whole bisect; the full report follows the steps: the trace stream, the plugin trace snapshot at the end, collect.sh. A plugin trace snapshot after every step is not on by default (about 50 MB uploaded per step, and the copy loads the guest while you look); by hand BISECT_PLUGIN_SNAP=1 sudo -E sh .../autoreport.sh --bisect-agdc does it.

The result: rdna3vm result prints the same table as bisect, and a second one with the counters of each step: swaps per head, copies, stale holds, zero-copy iop flips, buffers rewritten in place (the flicker you saw), torn buffers, frames copied by the display pipe, and the FRONT SURFACE lines of that step (live writer lines / sampler lines). It names the steps that looked right (your answers; black %, motion of the pictures) and the ones that looked broken, and the same by swap mode. The FRONT SURFACE column needs the kernel log: the serial log next to the report or the archive's 20-log-rdna3.txt. The kext samples the front surface only 40 times per boot, so if those were used up before the bisect the column says so (a WARN) and the inplace / torn counters are the evidence.

Play (step play): the desktop is yours

When you want to drive the desktop by hand (drag windows, open apps) and still get a full report:

The profile is the agdc step's (WindowServer runs on our Metal plugin, so the card works and its clocks are lifted) plus rdna3play=1. Do not use rdna3vm args "rdna3bisect=3" --stay for this: it has no agdc profile, the AGDC stays idle, WindowServer does no GPU work and no report is sent.

What happens: no test runs (no swap A/B, no mode switches, no apps, no gamma, no sleep). A notification says use the desktop; the report is taken at minute 5 and again at minute 10. The trace pump (accelerator and DRM trace streams, the plugin's trace snapshots) runs as in every step. At minute 5 (after the desktop has settled, about 90 s after boot) the run takes three scanout looks, the counters and rdna3_pmctl info and the full collection (collect.sh), and uploads it like any report (rdna3vm result picks it up). At minute 10 the same again, as a second report with its own name (the label is play). A snapshot of the trace stream is taken at each moment while the pump keeps running. Then the VM stays up: shut macOS down yourself (Apple menu), or the host stops it after 30 minutes. A report at shutdown is not possible (the shutdown gives the report script seconds, a collection needs minutes), so the second one is at minute 10.

The swap A/B is no longer part of a normal step (card run 2026-10-17d): add the boot-arg rdna3swapab=1 (rdna3vm args "<the step's args> rdna3swapab=1") to run it; it breaks the picture for a minute on purpose (mode 1).

The tests file says what this boot's WindowServer started with (== CoreDisplay prefs ...), triage prints it as present mode, CoreDisplay prefs.

Present-mode A/B (steps play-macpro, play-rootport, play-desktop)

Why: with our driver WindowServer presents with the legacy page-flip mode (CoreDisplay logs init_page_flip: page flip mode is on) and never sends IOPresentment transactions, while the NullMoth NVIDIA driver gets transactions. Two things in our VM differ from that setup, and a card run can tell whether either decides the mode:

  • The card is "integrated". IOGraphics sets IOFBIntegrated when the card's PCI bus number is 0 (fIntegrated = (0 == pciDevice->getBusNumber())), and the VM puts the card on the root bus (GPU_BUS=pcie0, 00:10.0). GPUWrangler then logs flags 0x10 (IG) ... b:d:f=0:16:0. Behind a PCIe root port the card is bus 1.
  • The Mac model is a muxed laptop. The OpenCore image says MacBookPro16,1; CoreDisplay logs isBDW=YES ... isMobile=YES and mux_initialize: Couldn't find any matches. A Mac Pro has none of that.

The three steps are the play step (the desktop is yours, reports at minute 5 and 10, the VM stays up) with one or both changed for that run only:

step Mac model card
play (as before) MacBookPro16,1 root bus (bus 0)
play-macpro MacPro7,1 root bus
play-rootport as in the config behind a PCIe root port (bus 1)
play-desktop MacPro7,1 behind a PCIe root port

Cheapest order: rdna3vm step play-desktop first. If the present mode changes there, run play-macpro and play-rootport to see which of the two did it (or whether it takes both); if it does not change, neither is the cause and the next suspect is CoreDisplay's own decision (tools/probe/coredisplay.sh, run by CI on the macOS runner, lists what the function that logs the mode reads). Each step is a normal card run: rdna3vm update, rdna3vm step ..., use the desktop for ~10 minutes (or just wait), shut macOS down, rdna3vm result, send the file.

Both can also be set for every run in ~/rdna3-vm/config (rdna3vm prepare keeps them): SMBIOS_MODEL="MacPro7,1" (also iMacPro1,1) and GPU_BUS="rootport" (default pcie0), or for one custom run rdna3vm args "<the step's rdna3 args> @smbios=MacPro7,1 @gpubus=rootport". The @ words are for the host: they are taken out of the boot-args macOS gets, and rdna3vm check prints what the config selects. An unknown @ word or an empty value (@smbois=..., @smbios=) stops the run with a message.

Nothing asked, nothing touched. rdna3vm edits the OpenCore config's SystemProductName only when a model was asked for (SMBIOS_MODEL other than MacBookPro16,1, or a step's @smbios=). With nothing asked, prepare, window, the install boot and every card step leave the OpenCore config as it is, exactly as before this feature (a config whose PlatformInfo/Automatic is false, which --smbios refuses, still works). If an earlier run wrote another model (play-macpro), the next run that asks for nothing writes MacBookPro16,1 back, so the model never outlives the step that asked for it; the host log says SMBIOS model: with the model, or SMBIOS model: not asked.

What changes in the VM with the model. Only PlatformInfo/Generic/SystemProductName of the OpenCore config. The serial number, board serial, UUID and ROM stay as they are, so the serial belongs to a MacBook model while the VM says it is a Mac Pro; that only matters for Apple's online services (iMessage, iCloud activation), which this VM does not use. macOS derives the board id (Mac-27AD2F918AE68F61 for MacPro7,1) from the model; the report records hw.model and board-id in 00-system.txt. Both desktop models are the kind the OpenCore sample configs use; iMacPro1,1 is only for the case MacPro7,1 boots badly (macOS 26 supports the Mac Pro, not the iMac Pro: an update from the installer may refuse it, a disk that is already installed boots).

Does a model change need rdna3vm approve again? Unknown. macOS records the "Allow" for a third-party kext by team and bundle identifier (/var/db/SystemPolicyConfiguration/KextPolicy) and builds the Auxiliary KC for the architecture, not for the model, so the approval should survive; nobody has tried it on this VM. Nothing is silent either way: the install boot and the approval window of a step run with that step's model, and if macOS then ran an old framebuffer/accelerator the run says STALE KEXTS old driver ran (triage, first line) and the host log names the model change (SMBIOS model changed since the last card run: A -> B). In that case run rdna3vm approve --step play-desktop (the window then runs that step's model; plain rdna3vm approve uses the config's; approve --card --step is refused, the card boot would use step 0's boot-args) and send the result so the open question in DRIVER-PLAN N39 can be closed. The messages that tell you to approve (the run's note, the queue stop, the triage's STALE KEXTS line) name rdna3vm approve --step <n> by themselves when the step used @smbios=.

The root port. GPU_BUS=rootport puts the card (VGA function 0 and the HDMI audio function 1, together) on pcie-root-port,id=rp0,hotplug=off. Earlier runs found the card unconfigured behind an unsized port (commits 0a80e3c, c21eed6), so the port now carries the windows the card needs: mem-reserve for the 32-bit BARs (2 MiB or more), pref32-reserve (512 MiB for the default 256 MiB BAR0, all BARs stay below 4 GiB as on the root bus) or, with a 64-bit window (RESIZE_BAR_LOG2 above 10, PCI_MMIO64_MB), pref64-reserve (a power of two above BAR0 + BAR2: 32 GiB for a 16 GiB BAR0) together with -global q35-pcihost.pci-hole64-size as large as OVMF's window. The sizes are read from the card's BARs after BAR0 was resized and printed in the host log (root port windows: ...). It is not proven on the card: OVMF only pads ports it treats as hot-plug capable, so with hotplug=off the real windows come from the BARs OVMF finds behind the port. If the report shows no AMD device or an unconfigured card, host-*.log has the guest's PCI bus at 8 and 40 s (info pci): send it, set GPU_BUS=pcie0 again, and judge play-macpro alone.

A new framebuffer build: allow it once

OpenCore injects the core kext itself, but RDNA3Framebuffer and RDNA3Accelerator load from macOS's own kext cache, and macOS takes a new ad-hoc signed build only after you allowed it. After rdna3vm prepare with a build that changed them (the reports say so: waits for approval):

rdna3vm approve

macOS starts in a window (the card and the screen stay with Linux) and stays up; about 2 minutes after the login System Settings → Privacy & Security opens by itself: scroll down, Allow next to the blocked system software, enter the password, then Not Now at the restart question and Apple menu → Shut Down. No Allow button there = already allowed, just shut down. rdna3vm approve --card does the same with the card passed through (the old way).

A queue that reaches a boot where macOS still runs the build allowed before stops by itself instead of testing it (rdna3vm queue status: stopped before step ...: macOS runs an older framebuffer/accelerator): rdna3vm approve, then rdna3vm queue goes on with the same step. Without that (builds before 2026-10-12) such a run shows the old framebuffer in its fallback console mode: everything redrawn about once a second, and before the fix of that mode black shown blue.

A new build reaches macOS without the card

A step or queue whose bundle (rdna3vm prepare / update) the VM does not have yet first boots macOS headless, without the card: Linux keeps the card and the screen for those ~3 minutes (== installing the new bundle in macOS without the card in the host log), macOS copies the new kexts and the Metal plugin's libdrm/RADV, and shuts down. Then the step starts with the card and already runs the new build: no install boot with the card that stops and runs the step again. Only a kext that really changed is installed again; a new framebuffer, accelerator or AGDC build needs the Allow above, and rdna3vm step / queue then opens the rdna3vm approve window by itself before the card step (Allow, Not Now, Shut Down: the card step starts after the window closes). rdna3vm prepare with the same build changes nothing in macOS. Should the headless boot not confirm the install (10 min limit, INSTALL_TIMEOUT_MIN in the config), the card step installs the bundle itself and runs once more, as before.

It is big3 (the default profile with amdgpu's exact sequence, user queues, PM control, VCN, mode set, HDMI stream / format / audio endpoint, display power) plus the output gamma, amdgpu's display-firmware reset, DC's extra steps around each mode switch, monitor standby and a short system sleep with the video engines on, and BACO last. Watch for: both monitors go to standby and come back, macOS sleeps ~30 s and wakes by itself, and at the very end BACO turns the chip off and on: the screens may stay dark after it - every result is already on the host by then, so just wait for the VM to stop (or use the emergency exit). Not in it (they need hardware or hands this bench does not have): dplink, dsc, mst, uhbr, odm (native DisplayPort monitors), subvp (a 120 Hz+ monitor), hdmi20 (a 4K HDMI 2.0 monitor), hotplug (someone at the cables); run them by name when you have that hardware. Before it, big2: macOS boots once and the report itself runs everything (DMA/GFX/Vulkan tests - buffers, a triangle, images, timeline semaphores -, Metal when the plugin is installed, the idle-power experiment, three looks at what each monitor shows, display sleep and wake, a switch through scaled modes, a 2-minute soak, the hang test last), then shuts down (about 12 minutes). Nobody needs to watch the screens; both monitors connected. While it runs, a Terminal window on the macOS desktop shows each test and its result (OK / FAIL), with notifications at the start and the end (/Users/Shared/rdna3-progress.log); closing it changes nothing. You can also name steps yourself: rdna3vm queue 5b 8c 9. The emergency exit stops the VM and the rest of the queue. If the computer reboots on the way (amdgpu could not take the card back), log in and run rdna3vm queue without steps: it goes on with what is left. At the end, rdna3vm result packs them into one file to send.

Step 9 in the VM: OpenCore sets the largest GOP mode (OC_RESOLUTION), so the desktop comes up at the monitor's native mode; only the monitor the GOP lit shows a picture. EDID comes over AUX for DisplayPort sinks and over the DDC (I2C engine) for HDMI and DP->HDMI adaptors. Read the framebuffer lines from the report (20-log-rdna3.txt); tools/triage_reports.py checks them. The VM will then not shut down by itself. Shut down macOS normally (Apple menu → Shut Down) or with the power button. The report is sent anyway.

The values we expect at each step are described in TESTING-HW. You do not need to check them, sending the reports is enough.

Emergency exit

Each of the methods below closes only the VM. The script then gives the card, keyboard and mouse back to Linux and restores the desktop:

  1. Both Ctrl keys at once, then Esc 3× (within 3 seconds). Both Ctrl keys take the keyboard away from macOS and give it back to Linux, and Esc 3× closes the VM. It works even when macOS hangs or has a kernel panic, because the keyboard is read by Linux, not macOS.
  2. A short press of the computer's power button. While the VM is running Linux does not shut down from it, it only closes the VM.
  3. You do nothing: an automatic step closes the VM by itself after 8 minutes (it usually finishes after about 3). With --stay the limit is 30 minutes. You can change both limits in ~/rdna3-vm/config (AUTO_TIMEOUT_MIN, TIMEOUT_MIN).

The script gives the card back to Linux even when QEMU itself crashes. The restore is hooked to the script's exit, not to macOS.

After the VM an RDNA3 card does not come back to Linux by itself (amdgpu logs DMCUB error / failed to blank crtc and the screen stays black). So after every step the computer sleeps for about 5 seconds and wakes up by itself: that powers the card off and on, and the desktop comes back. If amdgpu still cannot drive the card, the script reboots cleanly (the reports are already saved): wait a minute and log in. Settings in ~/rdna3-vm/config: RESTORE_MODE=suspend (default), auto (no sleep), reboot (always reboot).

Last resort, when nothing happens for 2 minutes after the VM closed: briefly press the power button (Linux shuts down normally), or hold it for 5 seconds. It does not harm the card.

The VM on this computer's real CPU (CPU_MODEL="host", AMD hosts; DRIVER-PLAN N53)

By default the VM shows macOS an emulated Intel Skylake CPU. For the planned bare-metal hackintosh on the same Ryzen the card can be tested with the real CPU instead: QEMU's -cpu host, and OpenCore gets the AMD_Vanilla kernel patches that every AMD hackintosh needs.

Switch (one line, nothing else to edit; rdna3vm changes the OpenCore image itself before every boot):

sed -i 's/^CPU_MODEL=.*/CPU_MODEL="host"/' ~/rdna3-vm/config      # the real CPU
rdna3vm check                                                     # the "VM CPU" part must be green
rdna3vm window                                                    # first try: macOS in a window, the card stays with Linux

Back to the Intel model (the patches are removed and what they replaced is restored the same way, no manual edit):

sed -i 's/^CPU_MODEL=.*/CPU_MODEL="Skylake-Client,-hle,-rtm,kvm=on,vendor=GenuineIntel,+invtsc,vmware-cpuid-freq=on,+ssse3,+sse4.2,+popcnt,+avx,+aes,+xsave,+xsaveopt,check"/' ~/rdna3-vm/config

What host does:

  • QEMU gets -cpu host,kvm=on,-kvm-pv-unhalt,+invtsc,vmware-cpuid-freq=on,check (more flags after host, in CPU_MODEL are appended). -kvm-pv-unhalt is required: without it macOS 26.4+ turns on paravirtual ticket locks and the first contended lock panics the VM on an AMD host (see the table below). The vendor stays AuthenticAMD: the patches expect it. +invtsc is the invariant TSC (macOS since Monterey panics when the host's TSC is not stable: rdna3vm check wants the host clocksource to be tsc). ignore_msrs is set by the VM start as before.
  • The topology is CPUS vCPUs = CPUS / CPU_THREADS cores x CPU_THREADS threads (CPU_THREADS in the config, default 1; +topoext is added for 2 or more, QEMU warns without it). The AMD core-count patch gets the same number of cores, so the topology macOS reads and the patch agree. With CPUS=12 that is 12 cores / 12 threads, patch 0C; the 5800X as it will be on bare metal is CPUS=16 and CPU_THREADS=2 (8 cores, patch 08).
  • Before every boot (window, step, the install boot) vmtool.py plist --amd-cpu <cores> writes 24 Kernel/Patch entries into the image's config.plist (their Comment starts with rdna3vm-amd:), sets Kernel/Quirks/ProvideCurrentCpuInfo and Kernel/Emulate/DummyPowerManagement on and the Cpuid1 spoof empty. What it replaced is kept in the key #rdna3vm-amd-restore of Kernel (OpenCore ignores # keys) and comes back with --no-amd-cpu, which every other CPU_MODEL runs. A second run changes nothing. The patch list is vendored in tools/vm/data/ (source, commit, licence and sha256 in amd_vanilla.SOURCE; the patches are not downloaded). Only the kernel patches are used, not AMD_Vanilla's IOPCIFamily ones (the VM's chipset is QEMU's; the bare-metal EFI of tools/baremetal/build_efi.py needs the "Disable 10 bit tags" ones for the B550 chipset, docs/BAREMETAL.html part 6).
  • The CPU name in About This Mac (RestrictEvents). macOS shows the Mac model's CPU ("8-Core Intel Xeon W" for MacBookPro16,1) whatever the VM has. In the same mode rdna3vm puts Acidanthera's RestrictEvents 1.1.6 and Lilu 1.7.2 into OpenCore (EFI/OC/Kexts + Kernel/Add, Lilu first); RestrictEvents patches that string for a non-Intel CPU and takes the name from CPUID, so no boot-arg is needed (revcpuname= would override it; it is left unset). The two RELEASE zips are the only thing rdna3vm downloads for the VM: once, into ~/rdna3-vm/oc-kexts, with the sha256 pinned in tools/vm/vmtool.py and tools/vm/data/oc_kexts.SOURCE (no network after that). The image's own Lilu is 1.6.8, which does not run on macOS 26; it is kept as Lilu.kext.rdna3vm-orig and put back, with RestrictEvents removed, by every run of another CPU_MODEL (or a host that is not AMD). A failed download is a !! RestrictEvents is not injected line in the terminal and host-*.log: the VM boots and only About This Mac keeps the Mac model's name. Check in macOS: About This Mac, and kextstat | grep -i -e lilu -e restrict (both listed; with -liludbgall/-revdbg a DEBUG build would log, the RELEASE one does not). Needs the VM: not run yet.
  • The run says what it did: VM CPU: ... and amd-cpu: on, 24 AMD_Vanilla kernel patches, core count 12 (0x0C) in the terminal and in host-*.log, and the result file's 00-host.txt has vm-cpu: lines (CPU, topology, the exact -cpu / -smp). In macOS: sysctl machdep.cpu.brand_string machdep.cpu.core_count machdep.cpu.thread_count shows the Ryzen and the counts above.

A bigger BAR0 for the VM (optional)

rdna3vm gives the VM the card with BAR0 cut to 256 MiB. That window is all the CPU can reach of the card's memory, and macOS's CPU-visible VRAM heap is what is left of it (144 MiB): WindowServer's framebuffers, the cursor and the swap copies share it with the buffers RADV maps. Card run 2026-10-17c ran it dry (the main display froze); the driver now keeps a reserve of it for the display (rdna3visreserve, docs/INSTALL-OPENCORE.html) and keeps buffers that need no CPU access out of it, so 256 MiB stays the default.

What macOS takes (DRIVER-PLAN N62, from Apple's IOPCIFamily source and card run 2026-10-28c): in a VM it keeps a PCI BAR only below 4 GiB (its PCI configurator drops 64-bit placements when CPUID says "hypervisor"), and on any machine it takes no BAR bigger than 1 GiB. Run 2026-10-28c had a 1 GiB BAR0 that OVMF put at 0x900000000 (its 64-bit window): macOS gave the card no BAR0 at all, the kext could not map it, the bring-up stopped and WindowServer never reached the GPU. So rdna3vm now gives the VM no 64-bit PCI window for a BAR0 up to 1 GiB, and OVMF has to fit it below 4 GiB. To try a larger window, put this in ~/rdna3-vm/config:

RESIZE_BAR_LOG2=9      # 2^9 MiB = 512 MiB (about 400 MiB visible heap); 8 = 256 MiB, the default

and leave PCI_MMIO64_MB unset (or 0). The host log then says OVMF 64-bit PCI window: 0 MiB (BAR0 512 MiB) and, in the guest's PCI bus at 8 and 40 s, BAR0: 64 bit prefetchable memory at 0x80000000 [0x9fffffff] (below 4 GiB). When that run is good, RESIZE_BAR_LOG2=10 (1 GiB) is the next try: it fits only if OVMF's 32-bit window has a free 1 GiB-aligned GiB, which q35 may not have. Values above 10 are useless to macOS (and the host log says so).

What the report must show (triage row VRAM aperture, the kernel's line VRAM aperture: BAR0 512 MiB at phys 0x80000000, mapped 512 MiB (kernel window, ...), visible heap N MiB): the same BAR0 size as the host's BAR0 ... -> 512 MiB, mapped equal to it, and VISIBLE VRAM with fewer or no refusals. VRAM aperture: NOT MAPPED: ... names why (for example the firmware put it above 4 GiB); a picture-less VM or an unconfigured card means OVMF could not fit the BAR below 4 GiB: set RESIZE_BAR_LOG2=8 again (or delete the line) and send host-*.log. The kext maps at most 1 GiB of BAR0 into the kernel (rdna3vramwin=<MiB> lowers it); a map that fails is retried with half the window down to 256 MiB, and the row then says WARN.

How it works (for the curious)

  • rdna3vm step N writes the step's boot-args to the OpenCore config.plist (a copy in ~/rdna3-vm/OpenCore-rdna3.img). Then, as a systemd service (rdna3vm-*, which keeps running after the desktop goes dark), it:
    • stops the desktop and detaches the console;
    • rebinds the card from amdgpu to vfio-pci;
    • starts QEMU with the card and the USB keyboard and mouse;
    • after the VM shuts down, gives everything back to Linux.
  • Before the VM starts, the computer also sleeps for 5 seconds (PRE_SUSPEND=1): that powers the card off, so the VM gets it cold, as after a fresh boot. Without it the card's boot screen (OpenCore menu) stays dark: the monitor reports no signal.
  • prepare sets OpenCore's UEFI/Output/Resolution to Max (OC_RESOLUTION in the config; empty = leave it): OVMF hands the card's GOP 800x600, and macOS keeps whatever mode the boot screen had.
  • QEMU reads the keyboard and mouse from Linux (input-linux, the "both Ctrl" toggle) and passes them to macOS as USB devices. Linux itself watches for Esc 3× and the power button (vmtool.py stopkeys, systemd-inhibit). After the VM the button works normally again.
  • prepare also copies the kexts into the OpenCore image (EFI/OC/Kexts, Kernel/Add), and OpenCore injects them at boot. macOS itself refuses our ad-hoc signed kexts ("invalid codeful kernel extension"). The copy in /Library/Extensions (from setup.sh) only provides the firmware files, which the kext reads from disk.
  • macOS sees Linux at the address 10.0.2.2. At that address tools/vm/vmtool.py serve serves the package and receives reports (only locally, 127.0.0.1:8000).
  • In macOS the org.rdna3.vmreport daemon collects a report 90 s after boot, i.e. tools/macos/collect.sh plus the rdna3_drminfo tests. It sends it and, if the host asked for it (rdna3vmauto=1), shuts down the system.
  • CPU_MODEL decides the VM's CPU (an emulated Skylake by default, the real one with host); rdna3vm adjusts the OpenCore image for it before every boot (see above).
  • The kernel log goes to the VM serial port (serial=3) into serial-*.log, and debug=0x100 halts macOS on a panic instead of restarting.
