We build Mesa's RADV on macOS with the amdgpu winsys unchanged: libdrm_amdgpu (the original, third_party/libdrm) + our libdrm core (userspace/libdrm_xnu), which talks to the kext instead of /dev/dri.

userspace/mesa/build_radv.sh build/mesa     # on a Mac with Xcode, meson, ninja, glslang, mako
# output: build/mesa/install/lib/libvulkan_radeon.dylib + radeon_icd.x86_64.json

build_radv.sh pins a Mesa commit (MESA_COMMIT, GitHub mirror), applies userspace/mesa/patches/*.patch and builds with -Dvulkan-drivers=amd -Dllvm=disabled (ACO, no LLVM). The CI job radv-macos (self-hosted macOS runner) does the same; its error summary is the port's task list.

Patches

Patch Purpose
0001-radv-open-render-node-through-drm_xnu RADV opens and closes the render node through drm_xnu instead of open(2) (physical device, its ac_drm device, and the winsys at vkCreateDevice), and does not stat it (no /dev/dri on macOS)
0002-addrlib-apple-branches-are-for-the-kernel-driver the __APPLE__ branches in addrlib are for Apple's kernel driver (NDA header, __umoddi3, IOPanic); we do not want them in userspace
0003-radv-darwin-weak-entrypoints-via-dynamic-lookup weak, undefined wsi_* symbols and optional entrypoints: ld64 on macOS requires -undefined dynamic_lookup
0004-darwin-use-libdrm_xnu-as-libdrm on macOS dep_libdrm = our libdrm: HAVE_LIBDRM, vk_drm_syncobj.c, u_sync_provider.c and wsi_common_drm.c build as on Linux (without this, vk_drm_syncobj_* did not exist and dlopen would fail)
0005-os_drm-ioctls-through-libdrm-on-drm_xnu util/os_drm.h (used by ac_linux_drm.c for every amdgpu query, CS, BO and VA call) calls ioctl(2) on the fd directly, bypassing libdrm; a drm_xnu fd is no kernel file, so RADV failed ac_drm_query_gpu_info and found no device (found with tools/radv_host.sh). On drm_xnu it goes through drmIoctl
0006-radv-bo-cpu-maps-through-drm_xnu RADV maps BOs with mmap(2) on the DRM fd after GEM_MMAP (not through libdrm), so vkMapMemory failed on drm_xnu; maps and unmaps go through drm_xnu_mmap / drm_xnu_munmap (placed maps at a fixed address are refused there)

libvulkan_radeon.dylib builds and links in CI. After linking, the script reads nm -m: a "dynamically looked up" symbol has no owner. Weak ones (weak.txt) get NULL at load time (optional entrypoints); non-weak ones (missing.txt) would make dlopen fail, so this list must be empty. SPIRV-Tools are disabled (-Dspirv-tools=disabled): they are only for debug dumps, and their symbols were not making it into the link.

vulkaninfo without a card

After building RADV, the radv-macos job swaps libdrm.2.dylib for libdrm_loopback.dylib (make -C userspace loopback: the same libdrm core on uapi/rdna3_drm.c in-process, loopback backend with software SDMA) and runs vulkaninfo --summary (when the runner has a Vulkan loader, e.g. the LunarG SDK) and rdna3_vktest --loopback. This is an end-to-end UAPI test without the kext: radv_physical_device queries everything it needs (DEV_INFO, HW_IP_INFO, FW_VERSION, MEMORY, SENSOR, GPUVM_FAULT, syncobj). The log is in the artifact radv-macos-logs/vulkaninfo.log.

RADV on a Linux host (no GPU, no CI)

tools/radv_host.sh builds the same Mesa commit with the same patches on Linux against libdrm_xnu with the loopback backend (-DRADV_DRM_XNU takes the patches' macOS branches: render node through drm_xnu, no /dev/dri inode to stat). It then runs userspace/rdna3_vktest --loopback: instance, physical device, device creation, and fill + copy on the transfer queue (the loopback executes SDMA only). Everything RADV asks of the UAPI at startup is exercised here first.

First result (2026-10-10): with patches 0001 (all three opens), 0005 and 0006, RADV enumerates "AMD Radeon RX 7800 XT (RADV NAVI32)", creates the device (general, compute, transfer, sparse families) and the SDMA fill + copy on the transfer queue verifies through libdrm_amdgpu -> drm_xnu -> uapi/. Before them, each of these failed in turn: no physical device (ac_drm_query_gpu_info), vkCreateDevice, vkMapMemory - all three would have failed on the card the same way.

The loopback cannot run shaders, so with RDNA3_LB_GFX_NOP=1 (rdna3_vktest --loopback sets it) GFX and compute jobs are accepted and fenced without running; their PM4 framing is still walked (every packet inside its IB, every chained INDIRECT_BUFFER on mapped VA). Result: all six submits (general, compute, transfer x 64 KiB / 256 B) pass; the transfer queue's data is verified. RDNA3_LB_TRACE=1 prints packet counts per job.

rdna3_vktest

userspace/rdna3_vktest.c loads the ICD directly (the VM has no Vulkan loader): device creation, then per queue family a 64 KiB fill + copy (RADV's compute meta shaders on the general/compute queues: a real ACO-compiled dispatch) and a 256-byte one (CP DMA), checked on the CPU. The radv-macos CI job builds it next to RADV; rdna3vm prepare --radv puts both in the VM bundle and the report runs it from step 8 on.

In the macOS VM (2026-10-10, tools/vm/macos/build_radv.sh, no card): RADV builds with 0 missing symbols and rdna3_vktest --loopback passes 8/8 there too, interop included. On Linux RADV on the real card the same test passes 8/8 (tools/linux/card_dump.sh).
